# Piece Balancer

## Header

Date: 2025-05-11

Owner: [Marton Elek](https://github.com/elek)
-

## Context

Storj distributes erasure-coded pieces across storage nodes. Over time the distribution becomes uneven: new nodes join empty, old nodes fill up, nodes are decommissioned, placement constraints change, and hardware failures require data to be reorganized. 

Today these situations are handled reactively (repair, graceful exit) or not at all (cold-data rebalancing). But repair is slow and resource intensive, as it tries to reconstruct the full segment from all the EC pieces. This is not required for the use-cases covered here, where we already have the healthy (or at least available) piece, just at the wrong place.

The problem is especially acute for Select placements where the node pool is small. Balanced placement is a key factor of free-space and throughput management.

There are two variant of the problems:

 * Bulk data transfer betwen servers (1->1). This is where we are able to move full log files (for example when we start new servers or decommission old servers)
 * More granular data transfer beween many servers

The second one is more simple to implement, but may (or may not be) slower. Especially because the random read limit.

The first approach supposed to be faster, but generates more complexity, and the Satellite database should be updated anyway.

There are other workarounds suggested (for example with updating piece_alias), but they have limitations.

### Use-Cases

#### 1. Node decommissioning (drain)

**Problem:** A storage node needs to be retired. All its pieces must be moved elsewhere before shutdown.

**Examples:**
- Decommissioning expensive hardware and transferring data to cheaper nodes.
- Adding new servers to a group and draining old ones.

**Current implementation (Drain observer):** The drain observer is configured with a node filter identifying nodes to drain. For each segment with a piece on a drain node, it selects a replacement using the segment's placement selector and generates a move job. This is similar to graceful exit but driven from the satellite side and integrated with the balancer worker.

#### 2. New node install

This is the opposite site: when new nodes are installed we may need to balanced to to them immediately to use it immediately.

#### 3. Disk-space balancing within a node group

**Problem:** Within a group of nodes sharing the same `last_net` (or another grouping attribute such as country or tag), some nodes are full while others have plenty of free space. Upload selection avoids full nodes, reducing effective capacity.

This is a variant of #2, but can be used not only for new nodes, but existing nodes.

**Examples:**
- After a failed drive is replaced, the new drive is empty while sibling drives on the same server are full.
- Moving data between instances on the same server, which are part of different placements

**Current implementation (Balancer observer):** The balancer observer computes the expected free space per node within each group. It identifies segments with pieces on "overfull" nodes (free space below group average) and generates jobs to move those pieces to "underfull" nodes in the same group. Only one piece per segment is moved per loop pass. The destination is validated against placement invariants before the job is created.

##### 4. Balancing across server groups

**Problem:** A placement spans multiple server groups. One group fills up while others have headroom. Or strategic redistribution is needed for better durability (surviving AZ failure).

**Examples:**
- One placement uses 4 server groups but one is full. Data should be spread to use all groups.
- Strategic move of data from one datacenter to other to improve datacenter-level durability.

**Current implementation:** The Balancer observer can target this by configuring the `Grouping` attribute. When grouping by a broader attribute (e.g. placement tag), the balancer moves pieces between server groups. Alternatively, the Invariant observer handles this when the desired distribution is expressed as a placement invariant.

##### 5. Fixing placement invariant violations

**Problem:** Placement rules evolve over time or are newly introduced. Existing segments may violate the new invariants (e.g. too many pieces in the same datacenter).

**Current solution (Invariant observer):** The invariant observer checks each segment against its placement invariant function. For segments with violations, it tries swapping violating pieces to new nodes and only generates a job if the swap reduces the violation count.

##### 6. (Future) Cheaper alternative to full repair

When a node fails, repair downloads enough pieces to reconstruct the segment and re-encodes new pieces. Balancer-style piece moves could be cheaper in cases where the piece already exists on another node and just needs to be relocated, avoiding the full reconstruction cost. This use-case is not currently implemented but the architecture supports it.


## Balancer: What We Already Have

The implementation lives in `satellite/balancer/` and consists of four components:

**Balancer observer** (`balancer.go`): Ranged-loop observer that identifies overfull nodes within configurable groups and generates piece-move jobs. Uses atomic counters to speculatively track free-space changes during a single loop pass. Validates all moves against placement invariants before creating jobs.

**Worker** (`worker.go`): Executes piece-move jobs with the following order of operations:
1. Fetch segment from metabase (validate it still exists and is healthy)
2. Classify segment pieces using repair health checks
3. Download piece from source node (with hash verification)
4. Upload piece to destination node
5. Atomically update metabase (CAS to replace source with destination)
6. Optionally delete source piece (or let GC clean up)

Supports both SHA256 and BLAKE3 hash algorithms. Verifies segment health before proceeding (won't move pieces from under-repaired segments).

**Drain observer** (`drain.go`): Identifies pieces on nodes marked for decommissioning and selects replacements using placement-aware selectors. Supports both per-placement selectors and a single override selector.

**Invariant observer** (`invariant.go`): Detects and fixes placement constraint violations. Only generates jobs that provably reduce violations.

**Queue:** Redis/Dragonfly streams (`XADD`/`XREADGROUP`) provide the job queue. Simple Push/Pop interface that can be swapped out. The `jobq` mmap-based queue was evaluated but doesn't support variable-size payloads needed for node IDs.

All components are registered as optional modules via the DI container (`mud.go`).

## Performance challengs

Initial performance mesurements showed some bottleneck regarding to the current implementation of balancer.

 1. Redis Queue operation required batching (implemented)
 2. Metabase operation requires batching (WIP). Guarantees are weakened, but should be fine.

We need to re-test the ops/sec what we can achieve with these optimization.

However randomized reads still can be a challenge, when the source instances are limited (coping only from a few nodes)

We also tried to do pure rsync based SN movement (without SN level piece-store overhead, or Satellite level segment updates). This supposed to show a theoretical ceil of any batch-based bulk data movement.

Challenges what we had:

 1. Originally SSH / tailscale limited to trhoughput (fixed)
 2. later we switched to pure rsync (36x process)
 3. We achieved ~7-8 Gbps, because network limitation
 4. Even at this speed, we have seen high w_await disk write times.

## Possible Ideas for Future Improvement

### A. High-throughput batch transfers (log-file level moves)

**Motivation:** HDD-based nodes are extremely slow with random-access piece transfers. Decommissioning a full node piece-by-piece can take weeks.

**Idea (from Jeff):** Add a hashstore API that sorts piece IDs by log-file offset. The satellite generates the set of pieces to move (as it does today), sends them to the source node in a batch download request, and the node returns pieces in sequential disk order. This dramatically improves HDD throughput.

**Challenges:**
- Segment metadata updates are still needed per-piece (Spanner is the bottleneck, not just disk I/O)
- Cannot derive segment ID from piece ID without a full scan; the satellite must still drive the process
- Does not eliminate the per-piece Spanner update cost

**Alternative idea (from Dan):** Transfer entire hashstore log files between nodes, then fix violations as a post-process. Log file = ~1GB sequential binary, very fast to copy.

**Challenges:**
- After copying a log file from node A to node B, some pieces may violate placement rules (the segment already has a piece on node B). With ~100 physical nodes and strict invariants, collision probability is high.
- Requires a "hashstore import" API on the destination node
- Needs hashtable merging or re-indexing on the destination
- Segment table still needs per-piece updates

### B. Container-based piece assignment (Ozone model)

**Idea:** Borrow from Apache Ozone's design where piece IDs encode a container ID. The satellite assigns pieces to containers, and containers map to log files. This makes log files transferable because the satellite knows exactly which pieces are co-located.

**Benefits:** Enables log-file-level moves with satellite awareness of placement implications.

**Challenges:**
- Requires a version byte in piece IDs (breaking change)
- Needs satellite-level compaction logic
- Container lifecycle management (open/closed states)
- Significant architectural change

### C. Piece alias table merging for node consolidation

**Idea (from Marton):** When merging storage nodes (not splitting), instead of updating every row in the segments table, merge the hashtables and modify the `piece_alias` table to remap aliases. This avoids the expensive per-segment Spanner update.

**Status:** Conceptual. Needs investigation into whether piece alias remapping is feasible without violating referential integrity.

** Challenges:**

- This works only when we merge full SNs, which is a veri particular use case
- It's useful only if we decommission node, and we have free space for the full node (which is not always true)

### D. Smarter node selection for new uploads

**Complementary approach:** Instead of only rebalancing after the fact, improve upload-time node selection to account for current free-space distribution. For Select warm data with TTL, this already works: balance uploads + wait for TTL expiry. For Select cold data, upload balancing alone is insufficient because old data doesn't expire.

### Alternatives considered

- **Graceful Exit (GE):** Existing mechanism for node decommissioning driven from the storage node side. The balancer's drain observer provides a satellite-driven alternative with better control and integration with placement rules. GE could potentially be reimplemented on top of the balancer worker.
- **Upload-only balancing:** For warm data with TTL, simply directing new uploads to empty nodes and waiting for old data to expire works. This does not work for cold data or when immediate rebalancing is needed.
- **jobq (mmap-based queue):** Evaluated as an alternative to Redis streams. The mmap implementation uses fixed-size records and doesn't support variable-length payloads (node IDs, piece metadata) without wasting memory. Redis streams support arbitrary fields and are operationally simpler.
